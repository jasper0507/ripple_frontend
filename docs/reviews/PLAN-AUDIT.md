# Bluebell 第一轮产品规划审计

日期：2026-10-04。审计人：独立 planning_audit subagent。本轮审计的是规划输入，尚未把最终 PRD、DESIGN 或前端应用判为通过。用户最新指令“不要做无彩色界面，允许蓝、紫、绿、红、黄”覆盖早期颜色禁用要求；审计不再把无彩色作为合格条件。

- 规划输入：[PLANNING-BRIEF](../research/PLANNING-BRIEF-INITIAL.md)、[ENGINEERING](../research/ENGINEERING.md)、[COMPETITORS](../research/COMPETITORS.md)。

- 第一方竞品材料只支持交互参考，未作为 Bluebell 的字段或能力来源。研究记录分别提供五轮工程搜索和六轮竞品搜索，写清了文本/源码观察与未做截图测量的边界。

分级：P1 表示会产生错误身份、结果或产品承诺，最终文档必须修订；P2 表示影响实施一致性和验收，需补全明确规则。本轮没有要求改后端的修复项。

## 发现与修订要求

### P1-01：401 重放缺少身份绑定，可能让旧草稿以新账号提交

**位置：** ENGINEERING 第二轮；PLANNING-BRIEF 关键行为第 4 条。

规划规定最多重放一次、退出/切换身份丢弃迟到响应，但没有明确「重放前核对请求原身份」。后端的登录和刷新返回独立 Access Token，JWT `sub` 是用户标识；另一个标签登录账号 B 后，共享 Cookie 已属于 B，而本页账号 A 的旧写请求可能仍在等待刷新。仅丢弃旧响应无法撤销已经以 B 发送的 POST。

**证据：** `internal/service/token.go:83`、`internal/service/auth.go:75`、`internal/handler/auth.go:84`；此处为跨标签交互推导，不声称后端提供身份切换协调。

**必须修订：** 记录写操作发起时的 `sub` 与会话代次；发送及 401 重放前重新核对。身份改变、退出或代次失效时不重放，保留草稿并要求用户重新确认发布。JWT 解码只帮助显示归属，不作为权限校验。只有后端明确返回受保护路由的 `401 UNAUTHORIZED`、且身份仍一致时，才允许一次认证刷新后的重放；网络异常、500、解析失败不能进入这一分支。

**验收：** A 标签提交前/401 后，B 标签登录另一个账号；不得出现旧草稿被新账号自动发布的请求。

### P1-02：退出失败没有定义，容易出现“已退出”后刷新又恢复登录

**位置：** PLANNING-BRIEF 产品范围、认证状态；ENGINEERING 第二轮。

后端先删除 Redis Refresh Token，再清 Cookie；删除失败会返回 500，清 Cookie 不执行。前端清掉内存 token 不等于服务端会话已注销。后端退出也不吊销已签发的 Access Token，不能承诺所有设备立即退出。

**证据：** `internal/handler/auth.go:146`、`internal/service/auth.go:67`、`internal/service/token.go:56`。

**必须修订：** 区分本地停止使用会话与服务端确认退出。500/断网显示退出结果未确认，清除本页写权限并停止自动恢复，提供再次退出入口；若用本地标记抑制恢复，写明跨标签传播、刷新后行为和何时清除。只有 204 才显示服务端退出完成。迟到刷新不能重新启用被退出流程清掉的会话。

**验收：** 退出 204 不解析 JSON；退出网络失败/500 后刷新页面不得无提示自动恢复会话；成功重新登录可以解除本地退出抑制。

### P1-03：写入结果不确定需要覆盖投票和删除，不能只覆盖发布

**位置：** PLANNING-BRIEF 关键行为第 5、8 条。

帖子创建先写 MySQL 再初始化 Redis，删除先软删 MySQL 再删 Redis；500 并不证明未写入。投票方向原本未知，或上一次操作已确认后再次操作遇到中断，都不能继续用旧选中态表达当前服务器方向。投票 PUT 成功但后续 GET 票数失败，是另一种状态。

**证据：** `internal/service/post.go:70`、`internal/service/post.go:104`、`internal/store/post.go:95`。投票状态读取路由未挂鉴权：`internal/router/router.go:56`，处理器从上下文读用户 ID：`internal/handler/post.go:275`。

**必须修订：** 所有写请求的网络中断/500/异常响应使用结果未确认状态且不自动重试。发帖保留草稿；删除先通过可用读取确认资源状态；投票写结果不确定时方向设为未知，票数刷新不能用来反推个人方向。PUT 成功且票数刷新失败时，保留已确认的本次动作，明确票数待更新。三个投票按钮都是设置动作；再次按赞成不自动变成取消。

**验收：** 分别模拟 POST、DELETE、PUT 的服务端已提交但响应丢失，以及 PUT 成功/GET 失败；界面不虚报失败或成功，不制造重复 POST，不通过 +/-1 猜票数。

### P2-01：正序评论分页缺少发布成功后的可执行落点

**位置：** PLANNING-BRIEF 关键行为第 7 条。

当前说明正确地排除了任意评论直达和补齐评论树，但未说明发表后用户在哪里看到新评论。评论按 `created_at ASC, id ASC` 分页，POST 只返回 ID；刷新当前第一页通常看不到新评论。总数和列表也不是一个保证无并发变动的快照。

**证据：** `internal/repository/comment.go:78`、`internal/handler/comment.go:106`、`internal/service/comment.go:124`。

**必须修订：** 明确成功后刷新总数、按服务端 `page_size` 计算末页、获取该页并尝试定位返回的 ID；若并发变动导致该页找不到，仍保留真实的“已发布 #ID”反馈及查看最新评论入口，不反复扫页寻找。删除最后一项后的越界页需要有界回退规则。页面外的回复目标显示 ID 和不可定位说明，不推断已删除。

**验收：** 第 1 页发表第 11 条评论、末页删除最后一项、发布期间其他用户同时评论、回复目标在别页或已被删除。

### P2-02：表单与响应约定仍不足以直接交给前端实现

**位置：** PLANNING-BRIEF 产品范围与工程约定。

简报列出了表单，但没有逐项约束和请求/响应矩阵。当前注册用户名仅 ASCII 字母数字、3–64 长度；密码仅字母数字、8–64；登录只要求非空及最长 64，不能套用注册最小长度。帖子标题最长 128，正文/评论后端没有声明应用层最大长度。注册成功不是登录成功。204 没有统一 JSON 包装。

**证据：** `internal/handler/user.go:23`、`internal/handler/auth.go:35`、`internal/handler/post.go:25`、`internal/handler/comment.go:25`、`internal/response/response.go:5`。

**必须修订：** PRD 写清字段限制、成功后动作和用户可见错误；DESIGN 列方法、路径、认证、实际字段、状态码/业务码、204 与非 JSON 错误处理。标题按后端字符语义计数；不擅设一个声称来自后端的正文上限。默认纯文本、保留换行并转义展示，不因竞品有富文本就引入 Markdown/HTML 编辑器。作者 ID 保持字符串；各数字 ID 的安全解析规则需明确。

**验收：** 注册/登录边界值、中文标题与 emoji 计数、纯空白输入的产品校验说明、HTML 文本展示、业务 403/404/409 与代理非 JSON 500、204。

### P2-03：票数与七日窗口要给出准确文案和状态有效期

**位置：** PLANNING-BRIEF 视觉草图及关键行为第 5、6 条。

后端返回 `up_votes` 和 `down_votes`，草图仅称“票数”，可能被实施者解读为净分。七日截止先于“新旧方向一致”的检查，因此到期后的取消和重复方向也会失败；个人方向 Hash 到期后删除，但总票数仍保留。浏览器本地时钟不等于 Redis 服务器时钟。

**证据：** `internal/handler/post.go:45`、`internal/service/post.go:316`、`internal/store/post.go:110`、`internal/store/post.go:196`。

**必须修订：** 直接标记“赞成 X / 反对 Y”，或显式标注净分是前端差值，不把净分叫赞成数。未知方向是独立状态；本页已确认操作不能被当作可恢复的历史数据。达到截止后停用三个写动作，保留统计，UI 的预估截止不能覆盖服务端 `409 VOTE_CLOSED`。说明重新进入、身份变化及跨标签操作之后如何使本地确认态失效。

**验收：** 已赞成再赞成、赞成改反对、未知时取消、截止前/后、客户端时钟偏差、刷新后方向未知且票数仍在。

### P2-04：新彩色方向需重做视觉状态实物，不能只更换色值表

**位置：** PLANNING-BRIEF 视觉方案；ENGINEERING 第一、五轮。

方案 A 的双栏与真实内容能力相容；没有发现借竞品塞入搜索、推荐、头像或评论数字段。用户已撤销无彩色要求，旧黑白灰约束必须在最终文件明确作废。色值和 ASCII 草图尚不足以评价现代感、中文密度和所有状态的一致性；允许使用颜色也不等于可以让颜色成为唯一状态信号。

**必须修订：** 使用新的彩色主题，并说明主色、辅助色与语义色的具体职责。PRD 至少附可打开的桌面列表、手机列表、帖子/回复、表单错误与删除确认视觉评审稿；样例内容标为虚构。DESIGN 固定字号/行高/间距/响应式断点，区分浅装饰线与可识别控件边界。选中、焦点、错误、成功、禁用、投票未知状态都辅以形状/文字/图标，不只靠色相或明暗差。视觉稿本身不声称等同可用应用或通过真实接口测试。

**验收：** 用最终实际配对检查正文 4.5:1、必要控件 3:1；在 320/390/768/1440、200% 文字放大及键盘操作下检查。44px 是本项目触控目标，不能写成 WCAG AA 的统一最低要求。

## 已核验可保留的取舍

1. 降级 GET vote 是有代码依据的：加 Authorization 请求头不能补上缺失的路由中间件；不使用返回 0 恢复个人方向是正确选择。PUT 仍在鉴权组内，可提供设置/取消三个动作。
2. 评论正序平铺和仅定位已加载目标符合当前接口；页面外目标不可得不等于已删除。
3. 删除操作由服务器校验作者，前端基于 JWT `sub` 仅减少无权限入口；不需要增造 `/me` 或用户详情接口。
4. 两栏、原生 URL 分页、窄票数区和阅读对齐可沿用。React Router 与 TanStack Query 职责清楚，不需要再增加通用 CRUD、全局业务状态框架或第二套请求客户端。
5. 没有推荐、成员数、通知、搜索、资料编辑等接口的入口继续排除。社区详情可以单独展示介绍，不必为社区目录逐项取详情。

## 本轮结论

**修订后通过（有条件，尚未闭环）。** 功能边界、投票降级和评论平铺有代码依据；彩色方向服从最新用户指令，待最终视觉稿评审。上述 3 项 P1 和 4 项 P2 必须进入最终 PRD/DESIGN/开发计划，再由第二轮独立审计逐项核对。此结论不是声称问题已修复，也不是批准进入应用编码或宣布可上线。
