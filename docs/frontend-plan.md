### 会影响页面和流程的约束

1. **公开浏览已纳入首版。** 社区列表与详情、帖子列表与详情、评论列表五类查询均已公开；这些接口不解析 Authorization，携带过期或无效令牌也不会因此返回 `401`。受保护业务写操作与查询本人投票状态仍需要 Bearer JWT。用户已在 Phase 4 确认游客可阅读，需要登录的操作再进入登录流程；这替代原先所有内容页都要求登录的设计。
2. **认证接口已实现，浏览器行为尚待验收。** 登录、刷新、退出及 Cookie 处理均已接通。登录 JSON 不含用户 ID 或 `expires_in`；刷新 JSON 仅含 `access_token` 和 `token_type`。JWT 的 `sub` 为用户 UUID，`exp` 为到期时间，不含用户名，见 [token.go](../../bluebell_backend/internal/service/token.go)。默认期限为 Access JWT 15 分钟、Refresh Token 7 天，配置命名空间为 `auth`，见 [config.go](../../bluebell_backend/internal/config/config.go)；未读取真实配置，前端不硬编码期限。刷新沿用剩余 TTL，不延长会话；后端仍无当前用户资料查询，冷启动恢复用户名以及跨标签页认证协调需明确后再实现。
3. **注册和登录校验不同。** 注册用户名为 3–64 位英文字母或数字，密码为 8–64 位英文字母或数字，两次密码必须一致。登录只要求非空且各不超过 64 个字符，不能套用注册的限制。
4. **分页固定每页 10 条。** 帖子和评论页码从 1 开始，不支持自定义 `page_size`。帖子按 `time` 或 `hot` 排序；评论按创建时间升序，同一时间按 ID 升序。
5. **列表字段有限。** 帖子列表不含正文、摘要、评论数或当前用户投票状态；社区列表只有 ID 和名称。按不存在的社区 ID 筛选帖子可能得到空列表，社区页应通过社区详情接口区分不存在与暂无帖子。
6. **详情页查询本人投票状态。** 受保护的 `GET /api/v1/posts/{postID}/vote` 返回 `data.direction`：`1` 为赞成、`-1` 为反对、`0` 为未投票或已取消，不含 `post_id` 或票数；读取方向不受 7 天投票窗口限制。帖子列表与详情仍不包含本人方向，匿名与登录查询的票数字段相同。用户已确认登录用户在详情页查询并展示本人方向，列表不逐条查询；尚未查询或查询失败保持未知，不能当作未投票。
7. **投票有 7 天窗口。** 从帖子创建时间计算，以服务端时间为准；到期后赞成、反对、取消和重复提交都会返回 `409 / VOTE_CLOSED`。
8. **回复不是完整评论树。** 评论与回复混合分页，通过 `reply_to_comment_id` 关联；回复目标可能在其他页或已删除，接口没有单条评论查询。仅凭当前页缺少目标，无法判断它已被删除。
9. **删除权限按内容作者区分。** 帖子作者不能删除他人的评论。删除评论后其回复仍保留；删除帖子后，详情、评论查询与创建、投票都返回帖子不存在。
10. **响应有例外。** 业务 JSON 为 `{code, message, data}`，失败时 `data` 为 `null`；删除和退出成功为 `204`，没有 JSON；健康检查直接返回各自对象。按 HTTP 状态和业务 `code` 区分错误，尤其是登录密码错误与会话失效两种 `401`。
11. **联调需要代理安排。** 默认后端地址为 `http://localhost:8080`，文档路径已含 `/api/v1`。后端未配置 CORS，开发和部署需安排代理或同源网关；不能重复追加 API 前缀。

### 当前接口不支持的能力

搜索、帖子或评论编辑、图片上传、个人资料维护、按作者查询“我的帖子”、找回密码、收藏、通知、社区管理和管理员管理均没有对应接口。首版建议不提供这些入口；如需纳入，先单独讨论约束和范围。游客浏览已由当前后端支持，并在 Phase 4 确认纳入首版。

刷新和退出已有实现及对应 OpenAPI，仍需核对它们能否满足已确认的浏览器共享会话、退出和异常恢复规则。不能因接口已实现就标记为前端已接入或验收通过；其余能力边界保持原约定。

- 评论按时间平铺，回复带目标引用。目标已加载时显示引用；未加载或不可获取时只显示评论编号，不直接断言已删除。
- 帖子和评论自动暂存草稿，刷新或本人重新登录后可恢复；提交成功或明确放弃时清除对应草稿，主动退出时清除该账号的草稿。关闭浏览器后不承诺恢复。
- 帖子列表和评论列表采用单页滚动浏览。后端仍按每页 10 条查询，前端自动分批追加；加载、位置恢复和新评论展示规则见下文。

### 用户流程

1. **注册与登录**：游客可直接浏览；访问发帖页或使用需登录的操作 → 登录页 → 可进入注册 → 注册成功返回登录并带入用户名 → 登录成功回到原站内目标，无原目标则进入首页，不自动提交先前操作。
2. **浏览**：游客和登录用户均可从首页最新帖子 → 切换最热或选择社区 → 在同一页面继续滚动浏览 → 打开帖子详情并阅读评论。同一标签页返回列表时恢复筛选、已加载内容和滚动位置；切换社区、排序或刷新页面时从顶部重新加载。
3. **发帖**：从首页或社区页进入发布页，未登录先完成登录 → 选择社区并填写内容 → 提交 → 用返回 ID 打开帖子详情。失败时保留输入；没有可选社区时说明原因并阻止提交。
4. **投票**：登录用户进入详情时读取本人方向，游客操作先登录 → 明确选择赞成、反对或取消 → 成功后更新方向并刷新票数 → 写操作窗口关闭时提示投票已结束。读取方向不受窗口关闭影响，未知与未投票分开，不依赖“再次点击同一方向即取消”的隐含状态。
5. **评论与回复**：游客可阅读，发表前需登录；在详情页发表评论，或选择某条评论作为回复目标 → 提交 → 成功后清理对应草稿并回显本次发布内容，保持阅读位置。评论按原顺序继续加载，加载到本次评论时合并展示；回复目标的引用与失效处理见下文。
6. **删除**：本人内容提供删除入口 → 二次确认 → 服务端确认成功后移除目标，删帖返回来源列表，无来源时返回首页。删除评论不连带移除其回复；受影响的分页列表暂停追加，提示用户从第一批刷新后继续，避免已知删除造成页码偏移漏读。刷新评论只重建评论列表并定位到评论区，保留帖子正文与草稿；并发删除造成的资源不存在状态需单独处理。具体规则见 Phase 4 的 Q9。
7. **认证续期、会话失效与退出**：公共阅读立即加载，会话在后台恢复。Access JWT 过期或受保护请求返回可续期的鉴权错误 → 由会话模块统一尝试续期；续期成功保留当前账号、草稿和业务缓存，已发送的写请求不自动重放。确认刷新凭据失效后 → 保留草稿、清理失效会话和账号相关状态；公开阅读页留在原处，访问发帖页或主动使用需登录的操作时再进入登录，并保留原站内目标 → 本人重新登录后恢复输入。临时网络或服务故障单独提示，不直接当作已退出。主动退出清理会话和对应草稿，刷新凭据的撤销与清除按新契约明确。登录密码错误留在表单，不触发续期；新契约的具体错误码在 Phase 4 核对。

### 已确认适配、状态与部署约定

1. **设备范围**：电脑优先，同时保证手机窄屏可完成全部业务流程；电脑保留主栏和辅助栏，手机改为单列并收起社区导航。主要浏览器为现代 Chrome、Edge。
2. **会话与草稿（按 Phase 3、Phase 4 后续确认更新）**：Access JWT 只保存在各标签页内存中；Refresh Token 通过持久的 HttpOnly Cookie 传递，服务端由 Redis 管理刷新凭据。同一浏览器共享一个登录账号，登录、换账号和退出影响该浏览器其他标签页，其他设备不受影响。页面刷新、重新打开标签页或浏览器后，刷新凭据仍有效且未撤销时自动恢复登录。草稿继续存入各标签页的 `sessionStorage`，按用户 UUID 隔离，评论草稿再按帖子 ID 区分，不同步草稿正文，关闭浏览器后不承诺恢复草稿。最终会话失效清理身份和账号相关缓存、保留草稿与公共阅读状态；主动退出时该浏览器各标签页清理该账号的会话、草稿及账号相关缓存，保留公共内容与阅读位置。换账号不展示或提交原账号草稿。公共查询与会话恢复并行，阅读页不因恢复缓慢或最终失效而强制跳登录。
3. **路由与状态分工**：React Router 使用 Data Mode（`createBrowserRouter`），负责路由、布局和路由错误边界；TanStack Query 统一维护服务端数据缓存；登录会话使用 React Context，表单与弹窗使用局部状态。社区和排序进入 URL，滚动位置及已加载列表放当前标签页内存。列表不因窗口聚焦或重新挂载而自动重排，并保留返回恢复所需的缓存；主动刷新、切换社区或排序按 Phase 1 重置。具体错误映射留到 Phase 4。
4. **部署与代理**：使用域名或独立子域名的根路径，由 Nginx 在同一个 HTTPS 入口提供前端静态文件和 `/api/v1` 反向代理，保留完整 API 路径；开发时由 Vite 代理相同路径。前端路由需要静态站点回退，API 错误不能回退为 HTML。此处确认的是部署方案，尚未检查或修改服务器、DNS、证书与 Nginx 实际配置。
5. **工具约束**：开发工具尽量轻量，减少初始安装项和配置维护量；具体工具链见下文。

上述会话规则由用户在 Phase 3 明确调整，替代原来的“会话存入 `sessionStorage`、各标签页独立、不同步登录与退出”；草稿的标签页隔离与关闭后不承诺恢复继续保留。Cookie 持久性和服务端有效期在 Phase 4 的新契约中对齐，自动恢复的前提是浏览器仍持有有效凭据。

### 已确认的模块职责与路由安排

沿用 Phase 2 已确认的浅层目录。用户已逐项接受模块划分与认证调整建议，职责与协作约定如下。

| 位置 | 职责 |
| --- | --- |
| `app/` | 组合路由、Provider、会话与共享布局；协调会话变化引起的缓存清理、草稿处理和导航 |
| `pages/` | 读取路由参数，组合 Query、表单与界面，决定页面级加载、空数据和业务错误如何展示 |
| `api/` | 维护生成类型、请求客户端、业务请求与 Query 定义；集中处理传输协议，不依赖页面与应用布局 |
| `components/` | 可复用的帖子列表、评论等界面；基础交互归入 `ui/`，页面专用内容留在页面附近 |
| `lib/` | 仅容纳实际复用的草稿存储、列表恢复等逻辑；不反向导入页面或布局 |

业务响应保留在各标签页的 TanStack Query，不再复制到 Context；会话由 Context 维护，表单和弹窗保留局部状态。URL 中的社区与排序、标签页内存中的列表恢复、`sessionStorage` 中的草稿继续遵循 Phase 2 更新后的约定。浏览器共享登录身份不等于共享 Query 数据、滚动位置或草稿正文。

首轮两项选择均已确认：

1. **数据加载入口**：页面使用 `api/` 中的 Query 定义加载数据，路由负责匹配、布局与访问控制，不使用路由 loader 预取业务数据。TanStack Query 是唯一服务端缓存。
2. **布局划分（按 Phase 4 更新）**：登录/注册使用独立、简洁的布局；首页、社区页、详情页和发帖页复用内容布局，内容布局本身不统一要求登录，发帖页与需要登录的操作分别检查会话。品牌和基础界面可以复用，前端访问控制不能替代后端鉴权。

### 已确认的会话与请求协作

用户已确认直接按短期 Access JWT + Redis Refresh Token 新契约设计。原先“Access Token 过期即跳登录”的处理由本节续期流程替代；不实现旧鉴权兼容模式。Refresh Token 使用 HttpOnly Cookie，Access JWT 仅存内存；同一浏览器共享账号，并支持有效期内自动恢复登录。下列职责已经明确，最新认证接口已提供，剩余差异在 Phase 4 最新规格复核中列出。

由请求层识别并上报错误，`app/` 的会话逻辑统一协调续期与最终失效。按 Phase 4 后续确认，公开查询不等待会话恢复，也不因 Access JWT 到期而先续期；最终失效时公开阅读页留在原处，需要登录的页面或用户操作才进入登录流程。请求层不直接操作路由或草稿。多个受保护请求共用同一会话的续期过程；最终失效只清理一次。旧会话的迟到响应不能结束新会话、回填新会话缓存或清理新会话草稿。最终失效清理身份与账号相关缓存，保留草稿、公共列表和阅读位置；主动退出仍按约定清理该账号草稿与账号相关缓存，保留公共内容与阅读位置。续期成功不清理这些状态。具体接线方式在 Phase 4 展开，不增加通用事件总线。

已确认的检查与重试规则：

1. **本地到期检查时机**：恢复会话、进入受保护页面或发起受保护请求前检查 Access JWT 有效期；发现过期时先协调续期。停留在编辑页面时不使用后台计时器强制跳转，草稿继续按已确认规则暂存。受保护请求的鉴权错误按新契约区分可续期、不可恢复与其他失败，本地检查不能替代服务端鉴权；登录、刷新请求不能递归触发续期。
2. **写请求重试策略**：发帖、评论、投票、删除等写操作不自动重试，也不在重新登录后自动重放；保留适用的输入，由用户再次操作。请求已发出但响应丢失时提示结果未确认，不能断言操作失败。具体错误分类、提示与可行的结果核对方式留到 Phase 4 和业务页面实现时展开，不承诺前端总能查明结果。

普通业务错误由对应页面展示：登录密码错误留在登录表单，评论追加加载失败保留正文与已有评论。最终会话失效、暂时无法续期与局部业务失败分别处理，具体错误码按新契约核对。

### 场景推演与职责核对

以下为基于新认证方案与已确认规则的设计推演，不是运行测试或接口联调结果。新接口提供后，在 Phase 4 核对可执行的协议细节。

| 场景 | 协作过程与应保留的约束 |
| --- | --- |
| 直接访问帖子详情 | 正文、评论与票数立即按公开查询加载，同时在后台恢复会话；身份确认前不查询本人投票方向，不执行受保护写操作。最终失效时保留阅读位置，用户主动使用需登录的操作再进入登录，保留原站内目标且不自动提交。 |
| 从列表打开详情再返回 | Query 保留已加载的帖子数据；列表恢复逻辑保留对应视图的滚动位置。返回时复用数据和位置；社区、排序切换或刷新页面按 Phase 1 重置。 |
| 正常发帖 | 页面维护输入，草稿按当前用户保存；用户提交后执行写请求，确认成功才清理对应草稿并用返回 ID 导航到详情。写请求失败或结果未确认时保留输入。 |
| 编辑过程中令牌到期 | 停留编辑时继续暂存草稿，不由后台计时器强跳；提交前发现过期则先续期，成功且仍是同一账号、操作未取消时才首次发送写请求。刷新凭据确定失效时保留草稿并进入登录；临时续期故障保留输入并提示。 |
| 受保护请求返回鉴权错误 | 请求层按新契约识别是否可续期；同一会话共用续期过程，确认不能恢复时统一清理身份与账号相关状态。阅读页不因后台本人投票状态查询失败而被强制跳走，主动需要登录的操作再进入登录。已经发出的写请求不因续期成功而自动重放；登录密码错误不进入续期流程。 |
| 本人重新登录或改用其他账号 | 本人登录后恢复各标签页对应账号的草稿，等待本人再次提交；换账号同步影响该浏览器其他标签页，清理旧账号相关缓存，保留公共内容与阅读位置，不展示或提交原账号草稿。旧会话的迟到响应对新会话无效，同一账号重新登录也遵循这一约束。 |
| 主动退出 | 撤销当前浏览器刷新会话并清除刷新 Cookie；各标签页清理该账号的内存凭据、草稿和账号相关缓存，保留公共内容与阅读位置，其他设备不受影响。前端隔离在途响应，后端撤销语义共同防止旧刷新结果恢复登录。具体接口及失败处理在 Phase 4 核对，不能仅靠删除 Access JWT 推断刷新会话已经撤销。 |
| 刷新页面或重新打开浏览器 | 启动时通过 HttpOnly Cookie 尝试恢复登录，公共查询同时加载；无有效刷新凭据时进入未登录状态并继续公开阅读，临时续期故障单独提示。页面刷新可恢复原标签页草稿，关闭浏览器后只承诺在凭据有效时恢复登录，不承诺草稿恢复。 |
| 多个标签页同时续期 | 各标签页先合并内部重复请求；跨标签页协调需与后端轮换语义配合，避免共享 Cookie 下的刷新竞态。不得把单标签页合并误当作浏览器级并发控制。 |
| 写操作响应丢失或退出时仍有请求在途 | 客户端不自动重试，也不能把取消等待当作服务端撤销写入；在结果未知时保留适用的输入，提示用户核对后决定下一步。 |

缓存更新继续受 Phase 1 的浏览规则约束：投票成功刷新票数，新评论按回显与合并规则展示；不能通过全局重取已加载帖子列表来破坏已展示顺序和返回位置。具体更新与失效规则归入业务 Query 定义，在实际业务实现时验证。

### 短期 Access JWT + Redis Refresh Token（已确认方向）

已接受的架构调整：

1. **区分 access token 过期与会话结束**：会话模块集中负责获取可用的访问令牌；发现过期时，由该模块决定是否可续期。页面不分别编写刷新逻辑。续期成功保持账号、草稿、缓存与阅读位置；确认刷新凭据无效或会话被撤销后，才进入统一失效流程。刷新遇到网络故障或暂时不可用时保留输入，提示暂时无法续期，不直接断言用户必须重新登录。
2. **保留现有模块依赖方向**：`api/` 负责刷新请求的传输与错误识别，`app/` 的会话逻辑负责续期协调与最终会话状态；通过具体调用接口衔接，请求层不反向导入应用布局，也不引入通用事件总线或多套鉴权策略框架。
3. **统一并发与迟到响应处理**：同一标签页、同一会话的并发续期共用一次刷新过程；跨标签页刷新必须与后端轮换语义共同协调。退出或切换账号后，旧刷新结果不能重新建立会话。前端忽略旧响应不能阻止浏览器处理其中的 `Set-Cookie`，因此还需后端撤销语义保证旧凭据不能恢复续期能力。具体协调机制随新契约确定，刷新请求自身不能递归触发刷新；采用凭据轮换时，刷新响应丢失后的恢复与重试方式必须由契约明确。
4. **区分首次发送与重放**：用户提交时若业务请求尚未发出，可以先续期，再在同一有效会话和未取消的操作下首次发送；已经发出的写请求继续遵守不自动重试、不在重新登录后自动重放的约定。接入 refresh token 不自动授权通用的刷新后重放中间件。
5. **凭据保存与持久登录**：Refresh Token 通过持久 HttpOnly Cookie 传递，不向页面脚本暴露其内容；Access JWT 仅存各标签页内存，不写入 `sessionStorage` 或 `localStorage`。启动时通过 Cookie 取得 Access JWT，关闭浏览器后在 Cookie 仍存在、服务端刷新凭据有效且未撤销时自动恢复登录。具体有效期由后端契约确定，客户端 Cookie 有效期与服务端期限需一致地表达该行为。
6. **浏览器内共享会话，草稿保持隔离**：同一浏览器共享一个账号，登录、换账号与退出同步影响其他标签页，其他设备不受影响。草稿正文、Query 数据和阅读位置仍按标签页隔离，草稿再按 UUID 隔离。换账号不带入原账号草稿；主动退出时该浏览器各标签页清理该账号草稿，最终会话失效保留草稿。后台或休眠标签页恢复操作前需要核对会话变化，不能仅假设它一定及时收到同步通知。

接入时点已确认：Phase 4 直接依据新契约设计和接入，不先实现旧接口下的过期登录流程。具体后端实现由用户负责，前端不修改后端代码。

用户已分别确认 HttpOnly Cookie、当前浏览器共享会话、有效期内自动恢复登录。这些选择替代 Phase 2 原会话存储与隔离约定；草稿关闭后不承诺恢复的边界保持不变。

Phase 4 接入前需对齐的新契约：

- 登录和续期的请求、响应、账号标识与展示信息、访问令牌有效期，以及 HttpOnly Cookie 的具体契约；前端不解析 Refresh Token 内部结构。
- 刷新凭据过期、撤销、轮换与重复使用的语义，尤其并发刷新或刷新响应丢失后的处理。
- 退出如何撤销当前浏览器的服务端刷新会话并清除 Cookie，保证其他设备不受影响；明确失败或响应丢失的处理、在途刷新竞态，以及已有 Access JWT 的剩余有效期如何处理。
- 哪些鉴权错误可以触发续期，哪些代表最终失效或临时故障；登录和刷新自身不进入递归刷新流程。
- Cookie 的作用域、HttpOnly、Secure、SameSite、持久有效期及 CSRF 防护契约，并与开发代理、同源部署和已确认的浏览器会话范围一起核对。

参考依据：[RFC 6749 §1.5](https://www.rfc-editor.org/rfc/rfc6749#section-1.5) 区分访问令牌与刷新令牌，[§5.2](https://www.rfc-editor.org/rfc/rfc6749#section-5.2) 描述确定的凭据失效错误，[RFC 9700 §4.14](https://www.rfc-editor.org/rfc/rfc9700#section-4.14) 讨论刷新令牌轮换与重用；这些资料用于核对设计概念，不预设 Bluebell 采用 OAuth 协议或相同错误码。[MDN Cookie 说明](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Cookies) 与 [sessionStorage](https://developer.mozilla.org/en-US/docs/Web/API/Window/sessionStorage) 的作用域差异用于复核标签页约定。

[MDN Set-Cookie](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Set-Cookie) 说明 Cookie 有效期、浏览器会话恢复与响应头处理；[RFC 6265 §4.1.1](https://httpwg.org/specs/rfc6265.html#section-4.1.1) 说明并发响应设置 Cookie 的竞态。由此推导出的架构要求是：跨标签页协调、迟到响应隔离和后端撤销需共同保证会话行为，不能仅靠单个标签页内的请求合并或丢弃响应实现。

### 已确认的写操作更新规则（Q9）

用户已于 2026-10-03 接受本项并确认阶段收口。全部在服务端确认成功后更新，不做提前显示成功的乐观更新，也不全局重取无限列表。

| 操作 | 确认成功后的行为 |
| --- | --- |
| 发帖 | 当前响应只含 ID；清理本次提交对应的草稿并打开详情，详情读取失败单独处理。返回来源列表时维持已有顺序，主动刷新后纳入新帖，不向旧分页头部硬插一条 |
| 投票 | 采用 PUT 返回的 `post_id` 与 `direction` 更新本人的方向；另取帖子详情取得票数，再按 ID 更新已加载列表中的票数，保持顺序。详情读取失败不把已成功的投票改判为失败，也不重发投票 |
| 评论或回复 | 当前响应只含 ID；以该 ID、本次提交正文与回复目标记录“已发布”的回显，不伪造服务端时间或完整响应实体。未读到底时保留阅读位置，后续列表读到同一 ID 后用服务端记录合并；已读到底时核对原末页并继续加载新内容，不能只请求下一个页码而漏掉原末页新追加项 |
| 删除帖子 | 确认 `204` 后移除缓存列表中的目标，清除该帖详情、评论及本人投票数据，返回来源列表；没有来源时返回首页。已受删除影响的分页列表保留其他条目，暂停追加，用户从首批刷新后继续 |
| 删除评论 | 确认 `204` 后移除目标及对应成功回显，保留回复；只有已确认删除的目标可标注已删除，单纯不在当前缓存中仍只显示编号。列表暂停追加，提示从首批刷新后继续；刷新只重建评论列表并定位到评论区，保留正文与草稿，失效的回复目标需由用户重新选择 |

删除后的暂停追加针对已知分页偏移：例如读过第 1 页的 10 条后删除其中一条，继续取原第 2 页可能跳过原第 11 条。首版由用户刷新列表后继续，不实现补页和重建全部历史的算法；这也不承诺能消除其他用户并发写入导致的页码分页遗漏。

写操作结果未确认时保留适用输入，不自动重发；网络失败或服务器错误均不能直接证明未写入。服务端已确认写入、随后读取失败时，分别表达“操作成功”和“数据暂未更新”。同一操作提交期间防止重复点击；成功回调只处理本次提交及其对应会话、草稿，不能清掉后来编辑的内容。

### 请求工具核查

- [`openapi-fetch` 的响应](https://openapi-ts.dev/openapi-fetch/#response) 分为 `data`、`error`、`response`；这里的 `data` 是完整响应正文，不自动解开 Bluebell 的业务信封。有 HTTP 响应的失败与网络异常走不同通道，统一错误处理需要同时覆盖，见[错误处理说明](https://openapi-ts.dev/openapi-fetch/middleware-auth#error-handling)。
- `204` 没有正文，不能通过 `data` 是否存在判断成功。删除 mutation 可以返回空结果；若某个 query 需要表达无值，应使用明确值如 `null`，不能成功返回 `undefined`，见 [Query Functions](https://tanstack.com/query/latest/docs/framework/react/guides/query-functions)。
- Query 依靠抛错或 rejected Promise 识别失败，原样返回失败对象不会自动进入错误状态。客户端 query 默认会重试 3 次，不能把该默认行为当作项目已确认的策略，见[错误识别](https://tanstack.com/query/latest/docs/framework/react/guides/query-functions#handling-and-throwing-errors)与[重试说明](https://tanstack.com/query/latest/docs/framework/react/guides/query-retries)。
- 请求需接收并传递 Query 的 `AbortSignal`，错误处理不能把主动取消混同网络故障；取消等待不代表服务端撤销写操作，见 [Query Cancellation](https://tanstack.com/query/latest/docs/framework/react/guides/query-cancellation)。
- [`openapi-typescript`](https://openapi-ts.dev/introduction#features) 生成编译期类型，不提供运行时响应校验；实际响应的状态、业务信封与异常正文仍需由请求层处理，具体检查范围在客户端设计中明确。
- 无限查询重新获取时会从第一页依次重取已缓存页，因此不能把普通全局失效当作保持顺序的更新策略；手动修改时保留 `pages` 与 `pageParams` 结构，见 [Infinite Queries](https://tanstack.com/query/latest/docs/framework/react/guides/infinite-queries)。
- `invalidateQueries` 默认重取活跃查询，`refetchType: 'none'` 只标记失效；还需单独控制后续挂载、聚焦和网络恢复时的重取。`setQueriesData` 可局部更新已存在的匹配缓存，见 [QueryClient](https://tanstack.com/query/latest/docs/framework/react/reference/classes/QueryClient)。这些机制服务于已确认的行为，不引入另一套实体缓存。

## 2026-10-04 投票模块（Issue #7）

详情页提供赞成、反对、取消三个动作。列表只显示公开票数，不逐条查询本人方向。缓存键是 `['votes', 帖子 ID, 'account', 用户 UUID, 本次会话]`，不含访问令牌。续期沿用这次会话。退出和换账号清掉该账号的方向，帖子和评论缓存留着。

方向 1、-1、0 是服务端确认过的结果，0 表示还没投或已取消。加载中、失败，以及本次还没拿到本人方向，都保持未知，不显示成未投票。游客点任何一个动作先去登录，回来后不自动投。提交中三个按钮都不可用。写入不自动重试，也不在重新登录后重放。网络故障或 5xx 说结果未确认。

PUT 成功后用回显写入这次登录的方向，再读帖子详情，按 ID 改已加载列表和详情里的票数，不重排、不重取列表。详情没读到时方向保留，并分开说明投票已记录、票数还没更新，不重发投票。回显的帖子对不上，或回调时已经不是这次登录，不写新会话的方向，也不把这次详情填回页面。`409 / VOTE_CLOSED` 表示投票已结束。结束提示和停用只留在当前这篇帖子、这一次登录；换帖、退出或换账号后清掉，迟到的回调不写到新页面。回到原帖再写仍由服务端决定。过期后本来仍应能读方向。

当前后端 HEAD `898460d` 已去掉 7 天窗口，OpenAPI 工作区也不再写 `VOTE_CLOSED`。前端快照仍保留该错误，页面继续按它处理，这次不把未提交的后端契约同步进来。`GET /api/v1/posts/{postID}/vote` 在 `686e802` 被挪到公开路由，处理器不解析 Authorization。2026-10-04 实测：带访问令牌投完赞成后再查询，仍返回 `direction: 0`。因此详情页暂时不发这个请求，方向只采用本次登录里 PUT 的回显；刷新后保持未知。后端开始按令牌识别用户后，把 `voteDirectionReadIdentifiesUser` 改为 true。验证见 [投票模块验证记录](verification/votes.md)。
